**Нода падает не от нагрузки, а от памяти.** Один скрипт, который ставит сервису границу
по RAM, включает ротацию логов и поднимает лимит дескрипторов — на Remnawave node и 3x-ui.
Ничего не правит в чужих файлах, показывает план до применения, откатывается одной командой.

```bash
sudo ./hubtune.sh             # меню: выбрать пункт и всё
sudo ./hubtune.sh status      # что не так прямо сейчас
sudo ./hubtune.sh plan        # что будет изменено, ничего не трогая
sudo ./hubtune.sh apply       # применить безопасный режим
sudo ./hubtune.sh apply --full # плюс swap, sysctl и BBR
sudo ./hubtune.sh rollback    # вернуть как было
```

Настраивать нечего: цель, объём RAM, версию cgroup, пути и имена сервисов скрипт находит
сам через метки Docker и systemd. Флаги нужны только чтобы отойти от умолчаний.

## Почему ноды умирают

### 1. Память

Xray-core растёт по RAM и не всегда отдаёт её обратно. Это не дефект конкретной панели —
это свойство ядра, обсуждаемое в апстриме годами. Свежий пример: начиная с Xray-core
v25.10.15 поменялись дефолты **xmux** для транспорта XHTTP (`maxConcurrency` был 32–16,
стал 1). Каждый запрос стал открывать своё соединение — на активной ноде это тысячи
одновременных сессий вместо десятков, и вместе с ними растёт память.

У 3x-ui своя история: после апгрейда 3.3.1 → 3.4.0 люди жаловались на 200+ МБ RSS
у самой панели на VPS с 1 ГБ ([issue #5549][i5549]). В релизе v3.4.1 появился пункт
`perf(memory): report real RSS and cut footprint via GOGC + periodic release` — то есть
проблема реальная и признанная.

**Что происходит, когда памяти не хватает и лимита нет.** Ядро зовёт OOM killer, и тот
выбирает жертву по «badness» — грубо говоря, по объёму потребления. Обычно это и правда
Xray. Но:

- перед убийством система успевает поболтаться в свопе и throughput проседает у всех
  клиентов сразу;
- жертвой может стать не Xray, а `dockerd` или `sshd` — и вы теряете не сервис, а доступ
  к серверу;
- после kill'а вы не узнаете, что это был OOM, если специально не полезете в `dmesg`.

**Что происходит, когда лимит есть.** Контейнер (или юнит) живёт в своей cgroup со своим
потолком. Как только Xray упирается — ядро убивает **только его**, `restart: always`
поднимает обратно за секунду, SSH и Docker живы, а счётчик `memory.events/oom_kill`
честно показывает, сколько раз это случилось.

> [!IMPORTANT]
> Лимит **не лечит утечку**. Он превращает «сервер отвалился, непонятно почему» в
> «сервис перезапустился за секунду, вот счётчик». Это разные аварии.

Для 3x-ui выигрыш ещё больше: панель **сама читает cgroup-лимит** (`memory.max` в v2,
`memory.limit_in_bytes` в v1) и выставляет Go-шный `GOMEMLIMIT` в 90 % от него. То есть
сборщик мусора начинает работать **до** того, как сработает OOM. Без лимита этого
механизма нет — Go считает, что памяти бесконечно.

### 2. Логи

Docker с драйвером `json-file` по умолчанию пишет **без ротации**. Лог контейнера растёт,
пока не кончится диск.

У 3x-ui лог самой панели (`/var/log/x-ui/3xui.log`) ротируется встроенным lumberjack
(10 МБ × 5, 7 дней, gzip) — тут всё в порядке. А вот **access.log самого Xray** пишется
ядром напрямую и не ротируется ничем: ни Xray, ни панелью. Это [issue #1234][i1234]
«Free disk space is constantly decreasing». Кончился диск → SQLite отвечает
`database is locked` → панель мертва, и связь с памятью тут нулевая.

### 3. Дескрипторы

- **Remnawave node** — в официальном compose уже прописано `nofile: soft 1048576 /
  hard 1048576`. Тут делать нечего, и скрипт это увидит и не полезет.
- **3x-ui** — ни в `x-ui.service`, ни в `install.sh`, ни в Dockerfile нет ни
  `LimitNOFILE`, ни `ulimits`. Xray запускается дочерним процессом внутри `x-ui` и
  наследует то, что дал systemd по умолчанию. Для сравнения: официальный установщик
  XTLS/Xray-install ставит своему юниту `LimitNOFILE=1000000`.

Под нагрузкой это выглядит как `too many open files` и обрывы у части клиентов при
живом и здоровом на вид процессе.

## Три режима вместо пятнадцати флагов

| Режим | Что делает | Что трогает |
|---|---|---|
| `--safe` (по умолчанию) | лимит памяти, ротация логов, дескрипторы, автоперезапуск | только сам сервис |
| `--full` | то же плюс swap-файл, сетевые sysctl, BBR | плюс настройки хоста |
| `--memory` | только границу по памяти | только сам сервис |

**Безопасный режим не выходит за пределы сервиса.** Всё, что он пишет, — это
override-файл рядом с compose (или systemd drop-in) и каталог бэкапа. Ни `/etc/sysctl.d`,
ни `/etc/fstab`, ни swap-файла. На арендованном VPS с чужой базовой настройкой это то,
что нужно.

**Полный режим меняет хост** — поэтому он отдельным флагом, а не по умолчанию.

Точечные `--no-*` перекрывают режим независимо от порядка:

```bash
sudo ./hubtune.sh apply --full --no-swap   # всё из полного, кроме swap
sudo ./hubtune.sh apply --no-swap --full   # то же самое
```

Запуск без аргументов в терминале показывает меню: короткую сводку по ноде и четыре
пункта — «безопасно», «полностью», «посмотреть», «откатить». В пайпе, в cron и при
`ssh host 'hubtune.sh'` меню не появляется — там по-прежнему работает `plan`,
который ничего не меняет.

```
HUBTune 1.0.0
  · Remnawave node (docker compose)
  · контейнер remnanode (running, перезапусков: 34)
  · RAM 1.9 GiB, swap отсутствует
  ✗ лимит памяти не задан
  ✗ сервис уже убивали по памяти: 7 раз
  ✗ ротация логов не настроена

  1) Безопасно   лимит памяти, ротация логов, дескрипторы.
                  Трогаем только сам сервис, хост не задеваем.
  2) Полностью   то же плюс swap, сетевые sysctl и BBR.
                  Меняет настройки хоста — смотри план перед подтверждением.
  3) Посмотреть  подробный отчёт, ничего не менять.
  4) Откатить    вернуть то, что сделал прошлый запуск.
  0) Выход

Номер:
```

Выбор пункта не применяет ничего сразу: сначала показывается тот же план, что и в
`plan`, и только после подтверждения идёт работа.

## Что именно делает скрипт

| Модуль | Режим | Docker | Нативный systemd |
|---|---|---|---|
| Лимит памяти | все | `mem_limit` + `memswap_limit` в override | `MemoryMax` (cgroup v2) / `MemoryLimit` (v1) + `MemorySwapMax=0` |
| Ротация логов Docker | safe, full | `logging: json-file, max-size × max-file` | — |
| Ротация `access.log` Xray | safe, full | — | `/etc/logrotate.d/hubtune`, режим `copytruncate` |
| Дескрипторы | safe, full | `ulimits.nofile` | `LimitNOFILE` в drop-in |
| Дескрипторы для сессий | full | — | `/etc/security/limits.d/` |
| Автоперезапуск | safe, full | `restart: always`, если политики не было | `Restart=always`, если её не было |
| Swap | full | только если RAM ≤ 2 ГБ и свопа нет | то же |
| Сеть (sysctl + BBR) | full | `/etc/sysctl.d/99-hubtune.conf` | то же |

Всё, что скрипт трогает, он предварительно копирует в
`/var/backups/hubtune/<метка времени>/` и записывает в манифест. `rollback`
проигрывает манифест в обратном порядке.

**`memswap_limit = mem_limit` означает, что контейнеру своп запрещён.** Это сделано
намеренно: своп-тряска на VPN-ноде — это скачок задержки у всех клиентов сразу. Лучше
быстро упасть и подняться, чем медленно умирать. Своп на хосте при этом остаётся —
он нужен системе, а не Xray.

## Установка

> [!CAUTION]
> Скрипт запускается от root и меняет боевой сервер. Никаких `curl … | bash` —
> сначала скачайте и посмотрите глазами.

```bash
curl -fsSL https://raw.githubusercontent.com/qwe8nxtroud/HUBTune/main/hubtune.sh -o hubtune.sh
less hubtune.sh
chmod +x hubtune.sh
sudo ./hubtune.sh status
```

Требуется: Linux, bash 4+, и либо `docker compose` v2, либо systemd. Зависимостей за
пределами coreutils нет.

`status` и `plan` — только чтение, ничего не меняют. Их можно смело запускать на боевой
ноде в любой момент.

## Как считается лимит памяти

Одна формула вместо лестницы из процентов:

```
запас_системе = ограничить(192 MiB … 20 % RAM … 1024 MiB)
лимит_сервиса = RAM − запас_системе
```

| RAM хоста | Лимит сервиса | Остаётся системе |
|---:|---:|---:|
| 512 MiB | 320 MiB | 192 MiB |
| 1 GiB | 820 MiB | 204 MiB |
| 2 GiB | 1.6 GiB | 409 MiB |
| 4 GiB | 3.2 GiB | 819 MiB |
| 8 GiB | 7.0 GiB | 1 GiB |
| 16 GiB | 15 GiB | 1 GiB |
| 32 GiB | 31 GiB | 1 GiB |

Логика запаса: системе нужно примерно фиксированное количество памяти — `dockerd`,
`sshd`, `systemd`, немного page cache. На 512 МБ это ~190 МБ, и «оставить 40 %» было бы
расточительством. На 32 ГБ те же 20 % — это 6 ГБ впустую, поэтому запас упирается в
потолок 1 ГБ. Отсюда и `ограничить(мин … процент … макс)`.

Переопределить:

```bash
sudo ./hubtune.sh apply --mem-limit 700m    # лимит вручную
sudo ./hubtune.sh apply --reserve 512m      # оставить системе ровно 512 МБ
sudo ./hubtune.sh apply --reserve-pct 30    # другой процент
```

## Почему override-файл, а не правка `docker-compose.yml`

Типовой «оптимизатор» вставляет строки в `docker-compose.yml` через `sed`. Так делать не
надо, и вот почему:

1. **Обновление ноды перезапишет ваш файл.** Установщики панелей регенерируют
   `docker-compose.yml` при апдейте. Лимит тихо исчезнет, и вы узнаете об этом
   при следующем OOM.
2. **`sed` по якорю бьёт мимо.** Классический приём — вставка после `restart: always`.
   Но у 3x-ui в compose стоит `restart: unless-stopped`, якорь не найдётся,
   `sed` молча ничего не сделает, а скрипт напишет «✅ готово».
3. **В проекте может быть несколько сервисов.** У панели Remnawave их пять
   (`remnawave`, `remnawave-db`, `remnawave-redis`, `remnawave-subscription-page`,
   `remnawave-caddy`). Вставка «после каждого `restart:`» повесит лимит и на Postgres —
   отличный способ уронить базу.
4. **Отката нет.** Обратный `sed` по уже изменённому файлу — это лотерея.

`HUBTune` вместо этого кладёт рядом отдельный файл:

```yaml
# managed-by: hubtune 1.0.0
# Базовый docker-compose.yml НЕ изменялся.
services:
  remnanode:
    mem_limit: 1639m
    memswap_limit: 1639m
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
```

Docker Compose подхватывает `*.override.yml` автоматически и сливает его с базовым.
Пересоздаётся при этом только нужный сервис (`up -d --no-deps`), а не весь проект — иначе
поднялись бы соседи, которые администратор намеренно остановил.
Базовый файл остаётся байт в байт таким, каким его сделал установщик — обновление ноды
его перезапишет, а override останется на месте. Откат — удаление одного файла.

Имя override выбирается под «диалект» базового файла: `docker-compose.yml` →
`docker-compose.override.yml`, `compose.yaml` → `compose.override.yaml`. Если в проекте
уже есть **чужой** override, скрипт откажется его трогать (пока не дадите `--force`).

Целевой контейнер тоже не угадывается по путям — скрипт спрашивает у самого Docker
compose-метки (`com.docker.compose.project.working_dir`, `…service`), так что работает с
любым каталогом установки.

## Почему НЕ нужен systemd-юнит поверх compose

Популярный совет — «создай `remnanode.service` с `ExecStart=docker compose up`, чтобы
нода поднималась после ребута и рестартовала при падении». Не надо:

- В compose уже стоит `restart: always`. Docker сам поднимает контейнер после падения
  **и** после перезагрузки хоста (при `systemctl enable docker`, что верно по умолчанию).
- Юнит с `Restart=always` поверх контейнера с `restart: always` — это **два супервизора
  на один процесс**. Они гоняют контейнер по кругу: Docker поднимает, systemd тушит
  через `docker compose down`, Docker снова поднимает.
- Обновление ноды делает `docker compose down/up` напрямую — и systemd считает это
  падением сервиса.

Вместо юнита `HUBTune` **проверяет** то, ради чего его заводили, и чинит только
если реально сломано:

```
· Автозапуск      restart=always, docker.service в автозагрузке: да
```

Если политики нет — добавит `restart: always` в override. Если есть — не тронет.

Отдельная проверка руками:

```bash
docker inspect -f '{{.HostConfig.RestartPolicy.Name}}' remnanode
systemctl is-enabled docker
```

## По платформам

### Remnawave node

Автоопределяется по образу `remnawave/node`. Ставит лимит памяти и ротацию логов.
`nofile` не трогает — в официальном compose уже `1048576`, и это правильное значение.

Из-за `network_mode: host` контейнер сидит в сетевом namespace хоста, поэтому sysctl
хоста действуют на ноду напрямую — BBR и очереди приёма имеют смысл.

### Remnawave panel

**Скрипт откажется работать на хосте панели** — жёсткий cgroup-лимит на `remnawave-db`
(Postgres) роняет базу: у Postgres свой `shared_buffers`, и он не умеет ужиматься по
требованию ядра. Панель определяется по контейнерам `remnawave`, `remnawave-db`,
`remnawave-redis`, `remnawave-caddy`, `remnawave-subscription-page`.

Если панель и нода стоят на одном сервере, скрипт выберет ноду и скажет об этом:

```
! На этом хосте рядом крутится панель Remnawave — трогаем только remnanode.
```

### 3x-ui в Docker

Определяется и по готовому образу `ghcr.io/mhsanaei/3x-ui`, и по локально собранному
(в официальном compose используется `build:`, а не `image:`, поэтому имя образа зависит
от каталога проекта). Опциональный сервис `postgres` из профиля не трогается.

В официальном `docker-compose.yml` строчка `mem_limit: 512m` есть — но закомментирована.
Скрипт её посчитает и раскомментирует по факту, через override.

### 3x-ui нативная (systemd)

Определяется по юниту `x-ui.service`. Здесь скрипт даёт больше всего:

- `MemoryMax` — которого в вендорном юните нет вообще, а панель умеет его использовать
  для `GOMEMLIMIT`;
- `LimitNOFILE=65535` — которого в вендорном юните тоже нет;
- ротацию `access.log` Xray через logrotate с `copytruncate` (Xray держит файл открытым
  и не переоткрывает его по сигналу — обычный `create` отправил бы запись в никуда).

> [!WARNING]
> **`StartLimitBurst` может оставить ноду лежать.** Вендорный `x-ui.service` приезжает
> с `StartLimitBurst=10` и `StartLimitIntervalSec=180`: если сервис упадёт 10 раз за
> 3 минуты, systemd **перестанет его поднимать вообще**. Слишком жёсткий лимит памяти →
> x-ui крутится в OOM-цикле → нода не встаёт сама. Скрипт предупреждает об этом сразу
> после применения.
>
> Снять запрет: `systemctl reset-failed x-ui.service`

### Что-нибудь ещё

Любой сервис docker compose:

```bash
sudo ./hubtune.sh apply --target имя-контейнера
sudo ./hubtune.sh apply --target какой-нибудь.service
```

Контейнеры, запущенные голым `docker run` (без compose), не поддерживаются — скрипт
скажет об этом прямо, а не сделает вид, что сработал.

## Откат

```bash
sudo ./hubtune.sh rollback
```

Берёт последний бэкап из `/var/backups/hubtune/latest`, проигрывает манифест в
обратном порядке (созданные файлы — удаляет, изменённые — восстанавливает, swap —
выключает и удаляет вместе со строкой в `/etc/fstab`) и поднимает сервис в исходном виде.

Откат срабатывает и **сам**: если во время `apply` что-то пойдёт не так — compose не
примет конфигурацию, контейнер не поднимется, лимит не применится — скрипт вернёт всё
назад, не оставив ноду лежащей.

Совсем вручную:

```bash
rm /opt/remnanode/docker-compose.override.yml
cd /opt/remnanode && docker compose up -d
```

---

## Чего скрипт не делает

Честный список, чтобы не было завышенных ожиданий:

- **Не лечит утечку памяти в Xray.** Если Xray течёт, он продолжит течь, только теперь
  падать будет он, а не ваш SSH. Причину лечат в конфиге: например, явными параметрами
  `xmux` (`maxConcurrency`, `maxConnections`, `hMaxRequestTimes`) для XHTTP.
- **Не является watchdog'ом.** Docker перезапускает *упавший* контейнер, но не *зависший*.
  Живой процесс, переставший обслуживать трафик, не поймает ни Docker, ни этот скрипт.
  В образе `remnawave/node` `HEALTHCHECK` отсутствует, так что и Docker тут не помощник.
- **Не трогает конфиги Xray, инбаунды, сертификаты и firewall.**
- **Не заменяет глубокий сетевой тюнинг.** Модуль sysctl здесь сознательно скромный.
  Если нужны XanMod-ядро, BBRv3, RPS/RFS/XPS и отключение THP — смотрите
  [jestivald/node-accelerator][accel]; задачи разные и инструменты дополняют друг друга.
  Единственное пересечение — файл в `/etc/sysctl.d/`; у нас он с префиксом `99-`,
  то есть применяется последним и перекрывает чужие значения. Если ставите оба,
  запускайте `HUBTune` с `--no-sysctl`.

## Грабли

**`docker compose up -d` поднимет ноду на том образе, который сейчас лежит локально.**
Если вы когда-то сделали `docker pull` и не пересоздали контейнер, `apply` заодно
обновит ноду. Скрипт это замечает, показывает оба хэша и спрашивает подтверждение —
не жмите `y` не глядя. Ломаный `:latest` в этой экосистеме — регулярная история.

**Пересоздание контейнера — это перерыв в обслуживании 2–5 секунд.** Клиенты
переподключатся, но короткий разрыв будет. Для нативной установки — 1–3 секунды.

**Учёт swap в cgroup.** Если ядро собрано без него, Docker напишет
`WARNING: Your kernel does not support swap limit capabilities` и проигнорирует
`memswap_limit`. Скрипт проверяет поддержку заранее и не пишет эту строчку.

**OpenVZ и LXC.** Swap-файл там создать нельзя, скрипт это определяет
(`systemd-detect-virt`) и пропускает модуль с объяснением, а не падает.

**Btrfs и ZFS.** Swap-файл на них требует ручной подготовки — модуль пропускается.

**Откат sysctl возвращает и значения в ядре.** Просто удалить файл из `/etc/sysctl.d/`
недостаточно — уже применённые значения (тот же `tcp_congestion_control=bbr`) живут до
перезагрузки. Поэтому перед правкой скрипт снимает текущие значения всех ключей, которые
собирается менять, кладёт их в бэкап и на откате применяет обратно поимённо.

**Базовый `docker-compose.yml` откат не восстанавливает** — намеренно. Скрипт его не
меняет, а копия в бэкапе лежит только для сравнения: между `apply` и `rollback` ноду
могли обновить, и возврат старого файла откатил бы заодно и обновление.

**Слишком маленький лимит опаснее отсутствия лимита.** Лимит ниже рабочего пика — это не
защита от OOM, а гарантированный цикл перезапусков. Скрипт сравнивает будущий лимит с
фактическим пиком и текущим потреблением и **отказывается применять** такой лимит без
`--force`:

```
✗ Лимит 820 MiB МЕНЬШЕ пика потребления (1.1 GiB).
  Сервис уйдёт в цикл перезапусков, а не защитится от OOM.
```

**Ниже 512 МБ RAM автоматический лимит не считается.** Формула на таком хосте даёт
значение, при котором Xray не живёт. Скрипт скажет об этом и предложит задать
`--mem-limit` вручную — остальные модули (логи, `nofile`, swap) при этом отработают.

**Несколько подходящих контейнеров — нужен `--target`.** Если на хосте две ноды или
рядом лежит мёртвый контейнер от неудачной установки, скрипт не станет выбирать молча:
он покажет список кандидатов с их состоянием и остановится. Иначе вторая нода тихо
осталась бы без лимита.

**Проект из нескольких compose-файлов поддерживается.** Если нода поднята как
`-f docker-compose.yml -f docker-compose.prod.yml`, скрипт прочитает весь список из
меток Docker и пересоздаст сервис со всеми файлами. Взять только первый — значит молча
выкинуть половину конфигурации.

## Все опции

```
hubtune.sh <команда> [опции]

Команды
  menu                меню (по умолчанию, если запущено в терминале без аргументов)
  status              состояние: лимиты, OOM-счётчик, пик памяти, логи, nofile
  plan                показать, что будет изменено (по умолчанию в скриптах и пайпах)
  apply               применить
  rollback            откатить последний apply

Опции
  --mode NAME         safe (по умолчанию) | full | memory
  --safe --full --memory   то же короче
  --target NAME       имя контейнера, ключевое слово (remnanode | 3x-ui | marzban)
                      или юнит вида x-ui.service. По умолчанию — автоопределение
  --mem-limit SIZE    лимит вручную: 768m, 1g, 1536m
  --reserve SIZE      сколько оставить системе; лимит = RAM − SIZE
  --reserve-pct N     доля RAM для системы в процентах (по умолчанию 20)
  --log-size SIZE     размер одного файла лога (по умолчанию 10m)
  --log-files N       сколько файлов хранить (по умолчанию 3)
  --nofile N          значение nofile (по умолчанию 65535)
  --no-mem            не трогать лимит памяти
  --no-logs           не трогать логи
  --no-ulimit         не трогать nofile
  --no-restart        не трогать политику перезапуска
  --no-swap           не создавать swap
  --no-sysctl         не трогать sysctl
  --no-bbr            sysctl настроить, но BBR не включать
                      (все --no-* перекрывают режим независимо от порядка)
  -y, --yes           не спрашивать подтверждений
  --force             разрешить рискованное: чужой override, цель-панель
  --no-color          без цвета
```

Массовая раскатка на парк нод:

```bash
for h in node1 node2 node3; do
  scp hubtune.sh root@$h:/tmp/
  ssh root@$h 'bash /tmp/hubtune.sh apply -y'          # безопасный режим
done
```

`-y` снимает подтверждения, но не отключает защиту: если расчётный лимит окажется ниже
реального пика потребления, `apply` всё равно откажется и вернёт ненулевой код — нода
не уйдёт в цикл перезапусков из-за того, что раскатку запустили без присмотра.
